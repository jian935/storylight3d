## 1. 30 秒陈述

> 写作者脑子里有画面，但要把它变成 3D，得先学建模、UV、材质——这是另一套技能。
> StoryLight3D 把这件事压成一句标记：在故事里写 `[[小精灵:character:发光的森林精灵]]`，
> 系统解析出实体，逐个调用 Aholo Lux3D 生成真实模型，再用 Three.js 按真实尺寸摆成一个
> 可以旋转、缩放、点击聚焦的场景。
> 它不是一个"3D 工具"，而是**让 3D 成为写作的副产品**——写到哪里，世界就长到哪里。

---

## 2. 问题：想造物的人，卡在哪里

| 卡点 | 具体表现 |
|---|---|
| **技能断层** | 写作者会写，但 3D 生产链（建模 → UV → 材质 → 灯光 → 渲染）是另一门手艺 |
| **流程断裂** | 现有 AI 3D 工具要求"上传图片"或"进另一个界面写 prompt"，创作被迫离开叙事现场 |
| **结果** | 文字里的世界只能停在想象；做 3D 变成"先成为 3D 从业者" |

这不是"3D 工具不够多"的问题，而是**入口放错了位置**：用户不是想学建模，是想让故事被看见。

---

## 3. 洞察：不要教用户建模，把造物藏进写作

- **3D 生成的价值不在模型本身，而在"叙事被看见"的那一秒。**
- 因此产品形态不该是"3D 编辑器 + 一个生成按钮"，而应是**写作界面 + 一层极轻的标记**。
- 类比：Markdown 之于排版。用户只多写几个符号，就换来了结构化能力；不需要打开排版软件。
- 设计约束由此确定：**标记必须能内联进散文、必须短、必须可被人类读懂**。

## 4. 产品定义与体验闭环

```
写故事（散文里内联标记）
   │  parseStory()
   ▼
实体列表 [{name, type, prompt}]
   │  逐个 / 并发
   ▼
Aholo Lux3D 文生 3D（GLB + PBR 材质）
   │
   ▼
Three.js 装配：真实尺寸归一化 → 分层布局 → 自动取景
   │
   ▼
交互：拖拽旋转 / 滚轮缩放 / 点击聚焦 / 切换故事
   │
   ▼
在线分享（静态站链接，带 sharecode）
```

每一环的用户可感知：

| 环节 | 用户看到什么 |
|---|---|
| 写 + 标记 | 左侧编辑器，标记与散文混排，不打断写作 |
| 解析 | "解析出的实体"列表，带类型徽章 |
| 生成 | 每个实体独立状态：`载入 42%` → `✓ Lux3D`；顶部总进度条 |
| 装配 | 3D 场景出现，实体按真实尺寸排列、带名字标签 |
| 交互 | 拖拽旋转、滚轮缩放、点实体镜头自动聚焦 |
| 分享 | 一个链接，打开即玩，无需安装 |

## 5. 关键产品决策（决策 / 放弃了什么 / 为什么 / 代价）

### 5.1 用内联 DSL，而不是表单式资产面板
- **决策**：`[[名称:类型:描述]]` 三段式，直接写在散文里。
- **放弃**：可视化属性面板的精确控制（位置、旋转、缩放滑块）。
- **理由**：一旦让用户填表，就退化成"3D 编辑器"，写作流被打断；三段式刚好够驱动生成。
- **代价**：用户要学 1 条语法；复杂空间关系表达不了（见 §9）。

### 5.2 只收敛 4 类实体，而不是"任意物体"
- **决策**：`character / creature / prop / scene`，类型决定目标尺寸与布局。
- **放弃**：无限类型带来的表达自由。
- **理由**：类型是布局的先验——角色 2.3、道具 2.0、场景 3.6（世界单位），否则"角色和房子一样高"。
- **代价**：类型外的东西只能归到 `prop` 或 `scene`，语义会变粗。

### 5.3 预生成资产优先 + 三档兜底，而不是纯实时生成
- **决策**：预生成 GLB → 实时 Lux3D → 占位几何体，逐级回退。
- **放弃**：永远"最新生成"的新鲜感。
- **理由**：演示/评审现场不能等每个资产约 5 分钟；同时避免把密钥暴露到前端、绕开 CORS；断网也能完整演示。
- **代价**：新增实体要重跑生成脚本（`scripts/generate_assets.mjs`）。

### 5.4 纯前端零后端，而不是账号 + 云存储
- **决策**：静态站，three.js 本地 vendor，无构建、无服务端。
- **放弃**：持久化、历史版本、多人协作。
- **理由**：部署成本≈0；用户故事不上传服务器（隐私）；链接打开即用。
- **代价**：刷新即丢编辑内容；没有"我的作品"。

### 5.5 自动取景 + 真实尺寸分层，而不是固定网格
- **决策**：按每类实体的真实包围盒算占地宽度，累加成一行并交替错位；相机按总量自动算距离。
- **放弃**：统一网格带来的整齐感。
- **理由**：模型尺寸差异极大，固定网格会让大场景挤爆、小道具消失。
- **代价**：极端构图（超宽/超高）仍需手动"重置视角"。

### 5.6 自建 IBL 环境光，而不是默认光照
- **决策**：用 PMREM 生成紫蓝青三色柔光箱环境贴图。
- **放弃**：写实影棚布光。
- **理由**：PBR 金属/水晶在没有环境贴图时会渲染成纯黑，这是最早暴露的观感问题。
- **代价**：整体偏"主题色"，不追求物理真实。

### 5.7 先做单场景陈列，而不是分镜/动画
- **决策**：一个故事 = 一个可交互场景。
- **放弃**：镜头运动、角色动画、视频导出。
- **理由**：先把"文字 → 世界"的闭环跑通并做稳，动画是下一层能力。
- **代价**：当前演示视频是录屏，不是应用内导出。

## 6. 技术如何服务体验（每条都对应一个用户可见结果）

| 技术处理 | 解决的用户问题 |
|---|---|
| 两段式 wrapper：内层缩放/落地，外层只摆位置 | 模型底部贴地、不悬空、不被二次位移覆盖 |
| 按类型目标尺寸归一化 | 角色/道具/场景比例合理，不像"同一套积木" |
| 并发加载 + 逐实体进度 + 总进度条 | 等待可见、不焦虑；知道卡在哪个实体 |
| 占地宽度累加布局 + 交替 z 错位 | 不重叠、不死板，有一点纵深 |
| 自动取景（按布局已知量算，不用含离群几何的包围盒） | 打开就能看全，不用手动找镜头 |
| PMREM 环境 + 三灯（天光/主光/双色补光） | 暗底上金属、水晶不发黑 |
| 失败回退占位几何体 | 永不白屏；坏一个不影响整体 |
| 点击拾取（Raycaster + 向上找 entity） | 点模型任意部位都能聚焦到整件实体 |

## 8. 差异化：它和已有东西到底哪里不一样

| 对比对象 | 它们的入口 | StoryLight3D 的入口 |
|---|---|---|
| 文生 3D（上传图/写 prompt 类） | 先有资产，再想怎么用 | **先有叙事，资产是叙事的产物** |
| AI 生图 | 输出平面图 | 输出**可交互 3D 场景**（旋转/缩放/聚焦） |
| 传统建模软件 | 学工具，精度高 | 零学习成本，**牺牲精度换可达性** |
| 游戏引擎 | 工程化、重 | 一个 HTML 打开即用，无安装 |

一句话：**别人做"生成模型的工具"，我做"让故事站起来的载体"。**

## 9. 边界与诚实说明

- **资产观感受 prompt 限制**：G1-Turbo 需要明确色相词才充分上色；早期"透明水晶/镜面/木制"等只描述材质的资产偏暗，已重写 prompt 并重新生成。
- **字幕是近似逐词对齐**：本环境 edge-tts 不返回 WordBoundary 时间轴，逐字高亮按字/词权重均摊，不是逐词精确。
- **DSL 表达力有限**：无层级、无相对位置（"在左边三步"）、无动画、无材质参数。
- **无账号 / 无持久化 / 无协作**：刷新即丢，不能多人同编。
- **移动端**是单列布局，性能取决于设备；复杂场景在低端机上会掉帧。

## 10. 如果继续做（按优先级，以及判断依据）

| 优先级 | 做什么 | 为什么是它 |
|---|---|---|
| **P0** | 故事分享页：把场景变成可传播的"故事卡片"（封面 + 一句话 + 场景） | 解决传播；当前链接是工具页，不是作品页 |
| **P1** | 风格一致性：同一故事的实体共享风格 token（色调/材质） | 解决"像不像同一个世界"，这是观感天花板 |
| **P1** | 分镜：一个故事 = 多个场景/镜头序列 | 从"陈列"升级为"叙事"，最接近产品初衷 |
| **P2** | 增量重生成：改一句只重生成对应实体 + 资产缓存 | 解决成本与等待（当前全量重跑） |
| **P2** | 定义"叙事还原度"评测：实体召回 / 尺寸合理性 / 人工 5 分制 | 把"好不好"从感觉变成可比较的指标 |

## 11. 面试问答（按真实情况准备，不编数据）

**Q1 你怎么发现这个需求的？**
A：我是写作者，也是 3D 的门外汉。我发现卡点不是"没有 3D 工具"，而是工具要求我先变成 3D 从业者。我把这个观察做成了一个可运行的假设：如果 3D 生成足够简单，它应该能内联进写作，而不是另开一个软件。

**Q2 为什么用 DSL，而不是做一个可视化编辑器？**
A：可视化编辑器会把产品变成"3D 工具"，写作流被打断。DSL 是刻意的约束：三段式（名称/类型/描述）刚好够驱动生成，又短到能写进散文。代价是表达力有限，我接受这个取舍，因为第一版要验证的是"入口"而不是"精度"。

**Q3 你怎么定义"做好了"？**
A：当前是黑客松 Demo，我没做用户测试，所以不报留存/满意度。我能定义的是三层可观测指标：① 实体解析召回（写得出的实体是否都被识别）；② 资产加载成功率（三档回退后是否仍能出场景）；③ 首次可交互时间（打开到能旋转）。如果要产品化，第四层才是"叙事还原度"的人工评分。

**Q4 有没有失败过一次，怎么改的？**
A：有。第一版资产在暗色场景里大面积发黑——因为 PBR 金属/水晶没有环境贴图。我做了两件事：一是自建 PMREM 三色柔光箱环境；二是发现 G1-Turbo 对"只描述材质"的 prompt 不上色，于是把所有 prompt 改写成带明确色相词的描述，重新生成。这是"技术问题"和"提示词问题"混在一起的一次排查。

**Q5 成本和延迟怎么样？**
A：单个资产约 5 分钟（Standard 档），这是文生 3D 的现实。所以产品上我没有做"每次都实时生成"，而是预生成 + 三档回退：演示和日常使用走预生成（快、稳、不暴露密钥），只有新增实体才触发实时生成。这是我用产品设计绕开技术延迟的例子。

**Q6 它的边界在哪？你为什么不去修？**
A：它不擅长复杂空间关系、动画、多人协作。我不修，是因为这些都属于"第二阶段"：第一版要证明的是"写作可以成为 3D 的入口"。如果入口不成立，做动画没有意义；如果入口成立，动画是自然延伸。判断优先级比堆功能重要。

## 12. English abstract

StoryLight3D turns prose into an explorable 3D scene. Writers inline lightweight tags
(`[[name:type:description]]`) inside a story; the app parses them, calls Aholo Lux3D to
generate real GLB assets with PBR materials, and assembles them in Three.js using
real-world size normalization, auto-framing, and click-to-focus interaction. It ships as a
zero-build static site with a three-tier fallback (pre-generated GLB → live generation →
placeholder), so the demo never goes blank. The project includes 10 real generated assets,
3 demo stories, a 12-page report, and a 47-second screen-recorded closed-loop demo. The key
product decision was to hide 3D generation inside the writing flow rather than building
another 3D editor: the value is not the model, but the moment a story becomes visible.
